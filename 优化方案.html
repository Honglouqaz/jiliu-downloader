一、实测：当前功能与真实速度

1.2 实测抓到的真 bug（已修）

❗ P1：引擎回退链顺序错误 —— aria2 失败后掉进单连接 curl

fallback_chain 的顺序是 curl → wget → native。实测中 aria2 一次失败后，任务被静默交给 curl（单连接）跑了 70 秒；而自研 native 引擎（8 线程）本可以用 8 秒跑完，却排在最后根本轮不到。已修：改为 native → curl → wget，并让回退日志带上失败原因（之前错误详情被吞，排查只能靠猜）。

已知待查（低频）

① 一次任务在 queued 状态停了 332 秒才开跑（仅出现一次，未复现，怀疑与 aria2 daemon 冷启动超时相关）；② 一次 aria2 addUri 失败导致回退（疑似同名文件残留 + continue 冲突）。两项都已加了日志可观测性，下次复现有迹可循。

1.3 速度结论

  • 引擎层不是瓶颈：native 8 线程 + aria2 双引擎，并发能力经受控实验验证达标（8 连接跑满 8 MiB/s 的服务器上限）。
  • 公网速度由源站决定：CDN 限速、B 站 PCDN 单文件限速是常态，IDM 在同样的源上也跑不快（实测同文件 1.55 vs 汲流 1.08 MB/s，同一量级）。
  • 与 IDM 的差距不在速度，在「接管体验」：见下节。

结论

汲流的协议覆盖已经是大一统水准（HTTP/BT/磁力/ed2k/迅雷链/网页视频/嗅探，且是国内软件里少见的不掺广告不绑架流量的）。真正的差距集中在「接管日常下载」的体验层：浏览器下载接管、调度队列、限速 UI、剪贴板监控——这四项恰恰是 IDM/AB 的核心卖点，也是「用户把默认下载器换成汲流」的临门一脚。

四、优化路线图（分四期）

Ⅰ

接管层 —— 让用户把默认下载器换成汲流（最高优先级）

  • 浏览器下载接管：插件用 chrome.downloads.onDeterminingFilename / webRequest 拦截普通下载点击，弹出「用汲流下载」确认条（AB/IDM 同款体验）。对视频站继续走嗅探逻辑，不冲突。
  • 剪贴板监控：主程序监听剪贴板，识别到直链/磁力时气泡询问（可开关，默认开）。
Ⅱ

调度与限速 —— 追平 IDM/AB 的管理能力

  • 队列与优先级：任务可拖拽排序、置顶；定时开始/暂停（凌晨挂机下载）。
  • 限速 UI：全局限速 + 单任务限速 + 时段限速（工作时间自动限速），native 引擎补 per-connection throttle，aria2 走 --max-download-limit（已有底子）。
  • 批量粘贴入队：输入框支持多行链接，自动识别协议逐条建任务（补 JDownloader 的核心场景）。
Ⅲ

体验细节 —— 差异化加分项

  • 边下边播：视频任务进度 > 5% 即可在详情页预览（MP4 range 请求即可，已有 server 基础）。
  • 动态分片增强：native 引擎借鉴 IDM——最快分片完成时立即把空闲连接调往最大剩余区间（现有 _claim 已是雏形，补「完成时再平衡」）。
  • 下载完成动作：杀软扫描钩子 / 自动解压 / 完成通知音（FDM 特色）。
Ⅳ

长线 —— 站点能力与生态

  • 网站爬取：输入列表页 URL，抓取媒体链接生成选单（FDM 站点抓取的开源平替）。
  • RSS 订阅（追更场景：番剧/播客/UP 主更新自动下载）。
  • BT 面板增强：做种管理、tracker 编辑、健康度显示（qBittorrent 对标，已有 bt 元数据底子）。
