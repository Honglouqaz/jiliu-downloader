二、方法：为什么必须分三层判

这份报告的前两版结论都是错的，错在把三个不同的问题混成了一个。 分清楚之后数据才可信，所以把方法写在这里。

层次问的问题怎么判要不要联网
1. 站点能力这个域名有没有解析器？ 枚举 yt-dlp 的 extractor 表，抠 _VALID_URL 里的域名 不需要
2. 链接形态yt-dlp 认不认这条 URL？ 官方 InfoExtractor.suitable(url) API 不需要
3. 真实结果实际能不能解出媒体？ yt-dlp --simulate -J（只解析不下载） 需要

第一版的错：拿站点首页去喂 yt-dlp。 首页必然回 Unsupported URL，于是 21 个站全被判成「yt-dlp 不支持」。

而首页从来就不是播放页 —— yt-dlp 设计上就不解析首页。 这个错误当时看起来「跑通了」，其实结论完全反了。

第二版的错：改用 _VALID_URL 抠域名之后， 建出来的表仍然是空的，于是又全判「无解析器」。

两个原因叠在一起：_VALID_URL 不一定是字符串（有些 extractor 写成 list），list.replace 抛 AttributeError； 而这个异常被外层一个宽泛的 except: pass 吞掉了 —— 表现为「跑通了但结果全是空的」，比直接报错难查得多。

修好之后表里有 1593 个域名，再展开 (?:cntv|cctv)\.(?:com|cn) 这类带分支的写法， CCTV 和 Twitter 才没被漏判成「无解析器」。

还有一个隐性错误：报告一度被写到项目根目录而不是 build/，而脚本照样打印「报告已写入」。 原因是 Path.with_name() 作用在目录上会把最后一段 （build）整个替换掉。这类「看着成功了、东西在别处」的问题， 只能靠写完立刻核对文件时间戳来发现。

链接从哪来

不看真实播放页就测不出真相，所以链接取三级来源：

  1. 登记链接（jiliu/sites.py 的 probe）—— 每个站维护一条当前有效的播放页；
  2. 自动发现（build/_discover_links.py）—— 抓站点首页/榜单页 HTML，正则出同域且路径匹配播放页特征的链接。 对纯前端渲染的站（爱奇艺、抖音、小红书）抓不到，改走它们的公开搜索接口 （如 search.video.iqiyi.com/o），从返回内容里正则出播放页；
  3. 人工核实 —— 前两条都拿不到时，用公开可核实的地址，并把来源写在脚本注释里。

四、这些结论落到了哪里

1. 写进代码旁边的注释。 每个站点的实测现状（哪家免登录、哪家要 Cookie、哪家链接会过期、哪家干脆不支持） 都记在 jiliu/sites.py 的 note 字段里。 改代码的人一眼能看到上次测出来是什么样，不用重新踩一遍。

2. 写进界面。 「站点」菜单直接展示这张表（国内/海外分组 + 每家现状）， 遇到不支持的站点会如实说「本站暂不支持」， 而不是让你等一个必然的失败。

3. 做成可重跑的脚本。 build/_test_cn_sites.py 可以随时重跑（全量约 1.5 分钟， --offline 秒出离线判定）。站点会变、上游会修， 这张表本来就不是一次性的。

4. 顺手修掉两个真 bug。 发现 sites.py 里两条过宽的路径特征把 API 端点误判成了播放页 —— Twitch 的 gql.twitch.tv/gql、Vimeo 的 progressive_redirect 直链。这类误判会让普通链接被硬塞给 yt-dlp， 白白失败一次。已收紧，并在测试里加了守护断言。
